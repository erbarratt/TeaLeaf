TeaLeaf Development Roadmap - Vertical Slice
============================================

Goal: a single greybox level (warehouse/docks) that runs in Play Mode and
showcases every core stealth mechanic end to end - sneak in, steal the
objective item, escape - with a fail/restart loop when caught. No settings
menu, main menu, save system or final art required.

Written 2026-09-26. Tick items off as [x] and log details in DEVLOG.txt.
[-] marks an item deferred to a later phase (the item says where).


Vertical slice feature list (agreed scope)
------------------------------------------
Movement:     walk, smooth/snap turn, gravity, crouch (done), sprint, jump,
              ledge climbing (done), mantling,
              ladders, rope climbing.
Visibility:   designer-placed shadow volumes (dark/lit areas), torches
              linked to the volume they light - extinguishing a torch darkens
              its area. Wrist-mounted visibility gem for feedback.
Noise:        footsteps by surface type (scaled by sprint/walk/crouch),
              thrown/dropped physics objects, doors and other interactions.
Guard AI:     patrol, suspicion, search, chase, catch (= fail + restart).
              Knockout state. Guards react to finding KO'd bodies.
Tools:        blackjack takedown, hand crossbow (either hand, physically
              cocked) with water / noisemaker / rope bolts, rotate-to-find-
              sweet-spot lockpicking.
Inventory:    wrist radial menu to select tools/bolt types; loot pickup and
              pocketing with a running loot total.
Bodies:       grab and drag KO'd guards to hide them.
Hands:        physical hands - the visual hand model collides with the world
              and stops at walls/props instead of passing through, then
              catches back up to the real controller position (Half-Life:
              Alyx / Thief VR style).
Art:          greybox (ProBuilder/primitives) for environment and props.
              Placeholder humanoid + Mixamo animations for guards. Existing
              real hand models with finger animation/grip poses.

Phase 1 - Locomotion completion (Player)
----------------------------------------
Scripting:
[x] Sprint: click-to-toggle on the left stick click (project-wide
    InputSystem_Actions Player/Sprint), sprintSpeed replaces moveSpeed.
    Ends when the stick returns to centre, on a second click, on crouch or
    on climb; can't start while crouched. Exposes IsSprinting. Verified
    in headset.
[x] Single MovementState (Still, Walking, Sprinting, CrouchStill,
    CrouchWalking, Climbing, Airborne) on PlayerLocomotion, so AI, noise and
    the wrist gem read one value instead of each re-deriving it. Moving is
    measured from real applied movement; Airborne after a short grace
    period. Verified in headset. Physical roomscale walking
    doesn't count as moving yet - revisit when guards perceive the player.
[ ] Ray-targeted climb grab + general hand snap poses. Climbing currently
    starts when a hand's SphereCollider overlaps a ClimbableEdge; change it
    so a hand grabs whatever its hand ray/reticle is on, and generalise
    the "hand snaps to a target" idea so ladders, ropes, doors, tools and
    props can all reuse it.
    [x] Grab trigger: holding grip while that hand's ray target
        (PlayerHandInteraction.LeftTarget/RightTarget) is a climbable
        starts the climb on that hand - held rather than press-only, to
        keep the old "hold grip and reach into a ledge" feel. The overlap
        check, ClimbableEdge.Active/Bounds/Overlaps/ClosestPoint and the
        climb SphereColliders are removed. Verified in headset.
    [x] Grab reach: decided - no separate grab distance. The hand ray is
        only 0.5m (rayLength), about arm's reach, so the ray is the reach
        limit. Revisit if it feels too far in headset.
    [x] General hand snap pose (Player namespace, used by any grab target):
        a small data type - e.g. a HandSnapPose struct with local position,
        local rotation and a hand animation pose/state - plus an interface
        (e.g. IHandSnapTarget) that a grab target implements to answer "given
        this hand (left/right) and this ray hit, where does the visual hand
        go, how is it rotated, and which pose does it play?". Handedness
        is part of the query, since the right hand is the mirrored left.
        Snapping is data on the target, not special cases in the hand code.
        (Verified in headset. HandPose enum, HandSnapPose readonly struct,
        IHandSnapTarget, all in Interaction. Hand offsets live in a shared
        HandSnapProfile ScriptableObject, per hand, so they're tuned once
        for every ledge.)
    [x] ClimbableEdge implements it: snap point = ray hit projected onto
        the edge's top-front line (clamped to the edge's length), rotation
        derived from the edge's orientation (palm down on top, fingers
        curling over the lip), pose = a "ledge grip" clip with the fingers
        bent over the edge. Tunable offsets per edge (or per edge type) so it
        can be lined up visually in the editor. (Position/rotation verified
        in headset; the finger pose is the PlayerHandAnimation item below.
        Convention: edge local X along the edge, +Y up, +Z out from the
        wall.)
    [x] Hand visual snap: on grab, the visual hand moves/rotates to the snap
        pose (short blend rather than a pop) and stays pinned there while
        gripping, replacing the current "pin visual at grab point" code in
        PlayerClimbing. Climb movement still uses the tracked controller's
        delta. On release, the visual returns to the controller. (Verified
        in headset: HandVisualSnap, placed last in the frame via
        PlayerClimbing.TickHandVisuals(); the visual is detached from the
        controller while snapped so it can't wobble.)
    [x] PlayerHandAnimation: a hand that is snapped plays the snap target's
        pose instead of input-driven curl. (A "Snap Pose" override layer
        whose weight follows HandVisualSnap.Weight, states named after
        HandPose values; HandState enum removed. Verified in headset.)
    [ ] Test: grab edges at chest and above head, at edge ends, and from
        steep angles; both hands on one edge; hand-off between hands; both
        mirrored hands look correct.
[x] Jump: a jump button on PlayerInputXR (right A is crouch, so e.g. right
    B / secondary button, via the project-wide Player/Jump action - check
    it's free of other bindings on both headsets). Only when
    grounded and not climbing; sets _verticalVelocity from a tunable
    jumpHeight (v = sqrt(2 * jumpHeight * -gravity), so height is what's
    tuned, not a raw speed). (Verified in headset. Bound to
    right B: the Player/Jump XR binding was <XRController>/secondaryButton,
    i.e. B or Y on either hand - narrowed to {RightHand}/{SecondaryButton}.
    Nothing in the XRI asset uses the secondary buttons.) Needs:
    [x] Horizontal air momentum in PlayerLocomotion: the thumbstick
        movement velocity at takeoff carries through the jump (running
        jumps travel further), added to _frameMovement while airborne,
        cleared on landing, cancelled against walls (CollisionFlags.Sides).
        (Climb release momentum was going to share this - removed.)
        (Built: one _horizontalVelocity, set from the stick while
        grounded and kept while airborne - walking off edges keeps speed
        too. After Move(), CollisionFlags.Sides replaces it with the
        velocity actually applied, so walls redirect it rather than kill
        it outright.)
    [x] Decide air control: light steering - the stick nudges airborne
        velocity at airControlAcceleration (3 m/s^2); centred stick bleeds
        it at airDrag (0.5 m/s^2).
    [x] Crouch interplay: decided - jump while crouched stands up without
        jumping (stealth-safe); a jump waits until the capsule is back to
        full standing height. Head clearance: instead of a pre-check,
        CollisionFlags.Above zeroes upward velocity, so a jump into a low
        ceiling bonks and falls rather than sticking to it. (Verified.)
    [x] Coyote time (a few frames of jump grace after walking off an
        edge) and a short jump buffer - small, cheap, feels much better.
        (Built: coyoteTime 0.1s, jumpBufferTime 0.15s.)
    [x] Grabbing a ClimbableEdge mid-jump works (existing reset of
        _verticalVelocity on climb start; also clears air momentum).
        (Built: climb start also clears horizontal velocity and any
        buffered jump.)
    [x] Landing: expose a Landed event with fall speed, for the landing
        noise (Phase 2) and a haptic thump. (Built: event Action<float>
        Landed, raised when grounded after Airborne.)
[ ] Mantling: when gripping a ClimbableEdge and the hand is pulled down past
    the edge top (or the head rises above it), smoothly move the player up
    and forward onto the surface above. Check clearance with a
    CapsuleCast at the destination first. Handle stand vs crouch
    clearance (auto-crouch if only crouch height fits).
[ ] Ladders: Ladder component (Interaction namespace) with rungs/grip
    volume, reusing PlayerClimbing's grab-and-pull-delta approach. Decide
    whether Ladder implements the same interface as ClimbableEdge or
    ClimbableEdge generalises into a "Climbable" base. Constrain movement
    to the ladder's vertical axis; mantle off at the top, drop off at the
    bottom. Grabbed via the hand ray like ledges, and implements the
    general hand snap pose: snaps the hand to the nearest rung with a
    ladder-specific position/rotation and a rung-grip pose.
[ ] Rope climbing: ClimbableRope (vertical line segment grab target) - built
    here so Phase 5's rope bolt only has to spawn one. Constrained vertical
    climb like ladders. Also uses the hand snap pose (hand wrapped around
    the rope at the grabbed height).
[ ] Gravity/fall interplay: releasing all grips mid-climb falls normally.
    Decide on fall damage (suggest: none for the slice).
[-] Climb release momentum: removed (2026-09-27). Built and tested -
    letting go kept the climb's velocity so pushing off a ledge launched
    the player - but it felt bad in headset and was taken out entirely;
    letting go drops from rest, as before. Measured with a debug logger:
    the body is locked 1:1 to the hand while gripping and players stop
    their arm before letting go, so a multi-frame average launch is a
    brake-then-kick stutter, and a seamless last-frame launch barely
    launches at all. See DEVLOG. Don't re-add without a new idea for that.
Animation:
[x] Ledge grip pose (HandPose.LedgeGrip) - fingers bent over the top of the
    ledge, supplied by ClimbableEdge's hand snap pose and played while that
    hand is snapped (see the ray-targeted climb grab item above).
    Hand_L_LedgeGrip keys joints 1-3 of all four fingers. Verified in
    headset.
[ ] Ladder rung and rope grip poses (can reuse the ledge pose initially),
    supplied by Ladder/ClimbableRope snap poses.
Test scene:
[ ] Extend the CharacterController test scene: ledge at chest height, ledge
    above head, mantle onto low-clearance shelf, 4m ladder, rope, a gap to
    jump across, a jump up onto a low crate, a low ceiling over a jump spot.


Phase 2 - Core stealth framework (Core namespace)
-------------------------------------------------
[ ] GameState/LevelManager: Playing, Caught, Won. Restart the level on
    Caught (fade to black, reload scene). Won when the objective item is
    carried into the exit zone.
[ ] Screen fade: simple fade-to-black sphere/quad around the head camera
    (used for caught, restart, level start).
[ ] Noise event system: NoiseSystem static/singleton with
    Emit(position, loudness/radius, NoiseType, source). Listeners (guards)
    register on enable. No per-frame allocation - use a struct payload.
[ ] Shadow volumes: ShadowVolume component (trigger box) with a darkness
    value. PlayerVisibility (Player namespace) tracks which volumes the
    player's body/head is inside and outputs a single Visibility 0-1.
    Default outside any volume = lit.
[ ] Light-to-volume linking: LightSource component (torch, lamp) holds
    references to the shadow volume(s) it "lights". While lit, those
    volumes count as lit; when extinguished, they revert to dark. Also
    toggles the light, flame VFX and audio.
[ ] Stance modifies visibility: crouching lowers it, sprinting raises it.
    Keep the multipliers as serialized fields for tuning.
[ ] Surfaces: SurfaceType enum (Carpet, Wood, Stone, Metal, Water, ...),
    mapped via a small SurfaceTag component or physics material lookup.
[ ] Footsteps: PlayerFootsteps measures horizontal distance travelled,
    emits a step every N metres, raycasts down for SurfaceType, plays the
    surface sound and emits a noise event scaled by surface x stance.
    No steps while climbing or airborne. Landing (from a jump or fall)
    emits a noise event scaled by fall speed x surface - jumping is loud.
[ ] Debug (Scripts/Core/Debug): on-screen/world-space readout of current
    visibility, stance and last noise; gizmos drawing shadow volumes and
    noise radii.


Phase 3 - Interaction framework (Interaction namespace)
-------------------------------------------------------
Physical hands (Player namespace) - build this first, since grabbing,
tools and climbing all sit on top of where the visual hand ends up.
Claude to guide this step by step, starting with a comparison of the most
performant approaches for Quest 3 before any code is written:
[ ] Separate the visual hand from the tracked controller: the controller
    transform stays the "target", the visual hand is its own object that
    tries to follow it every frame.
[ ] Hand colliders: a small set of cheap primitive colliders per hand
    (e.g. a palm box/capsule plus a few finger capsules - no mesh
    colliders) on the PlayerHands layer, colliding only with Environment/
    Interactable (layer matrix from Phase 0; Climbable is deliberately off -
    ledges rest on the Environment geometry). Revisit PlayerHands-Guard.
[ ] Collision response: when the target moves into geometry, the visual
    hand stops at the surface and slides along it rather than
    penetrating. Evaluate options together: kinematic sweep/depenetration
    (CapsuleCast / Physics.ComputePenetration, no Rigidbody - likely the
    cheapest and most predictable) vs a velocity-driven Rigidbody hand
    (lets hands push physics props, costs more physics time).
[ ] "Elastic band" catch-up: once the path is clear the visual hand
    returns to the controller position quickly but smoothly (no pop).
    If separation exceeds a max distance (e.g. 0.3-0.5m, tunable) or the
    hand is stuck, snap straight back to the controller.
[ ] Rotation follows the same rule (hand rotation blocked by contact,
    then eases back).
[ ] Integrate with existing systems: a hand snapped to a grab target (hand
    snap pose, Phase 1) must take priority over the physical follow.
    Decide whether hand rays (PlayerHandInteraction) - which now also
    drive climb grabs - use the tracked or the visual hand (probably
    visual, so you can't grab through a wall). Held items/tools inherit
    the visual hand's position.
[ ] Optional feedback: light haptic pulse on first contact; faint "ghost"
    hand at the real controller position while separated (as Alyx does).
[ ] Test scene: wall, table edge, pillar corner, a gap narrower than the
    hand; verify no jitter against surfaces and no tunnelling on fast
    swings. Profile the cost on Quest.
Grabbing and props:
[ ] Decide grab approach: custom grab consistent with PlayerClimbing
    (recommended - one system, one set of hand states) vs XRI interactables.
    Build IGrabbable (or a Grabbable base) alongside the existing
    IHighlightable pattern.
[ ] Grabbable physics props: pick up, hold, release; throw using velocity
    averaged from the last few frames of PlayerTracking hand positions.
[ ] Impact noise: ImpactNoise component emits a noise event on collision
    above a speed threshold, loudness scaled by impact speed + surface.
[ ] Doors: hinged door, grabbed by handle and swung by the hand (or push to
    open), with Locked state, creak noise event while moving, and NavMesh
    obstacle/link updates so guards can path through.
[ ] Grab hand poses: hold-object pose per hand, as a new HandPose value +
    Snap Pose layer state. Grabbables, door handles and tools supply their
    hold position/rotation/pose through the same hand snap pose interface
    as climbables.
[ ] Highlighting: grabbables/doors/locks implement IHighlightable so the
    existing hand ray + reticle system works for them unchanged.


Phase 4 - Inventory and wrist radial menu (Inventory + UI namespaces)
---------------------------------------------------------------------
[ ] Inventory data: owned tools (blackjack, crossbow, lockpick), bolt

[ ] Wrist radial menu: hold a menu button on one hand; a world-space radial
    appears on that wrist; select with the other hand's ray or the
    thumbstick; release to equip into the OTHER hand (so either hand can
    hold any tool).
[ ] Equip/unequip: spawn or enable the tool model in the chosen hand,
    snap that hand to the tool's hold pose, unequip back to
    empty hand from the menu.
[ ] Bolt type selection: a submenu (or a second ring) on the radial for
    water / noisemaker / rope, greyed out at zero count.
[ ] Wrist display: visibility gem + loot total + bolt counts on the
    non-menu wrist (or the same wrist, when not in menu mode).
[ ] Loot: Loot component (value, highlightable, grabbable). Grab it and
    release it inside a hip "pocket" trigger zone to collect it: plays a
    sound, adds to the total, and destroys/pools the object. Objective item
    uses the same flow with an extra flag.
[ ] Performance: world-space canvases only enabled while visible; no
    layout rebuilds per frame; update text only when values change.


Phase 5 - Tools (Player / Interaction namespaces)
--------------------------------------------------
Blackjack:
[ ] Greybox blackjack model and hold pose.
[ ] Swing detection: blackjack tip velocity above a threshold on contact
    with a guard's GuardHead collider.
[ ] Takedown rules: works only if the guard isn't in Chase/Alert and the hit
    comes from behind (dot product of the guard's forward vs the hit
    direction). Otherwise it makes a noise and the guard becomes alerted.
[ ] Haptic pulse on hit; thud noise event.
Hand crossbow:
[ ] Greybox crossbow with separate moving parts (string/lever, bolt slot)
    usable in either hand; mirrored hold pose per hand.
[ ] Physical cocking: the other hand grabs the lever/string and pulls it
    back past a threshold, then the crossbow is cocked. Auto-loads the bolt
    type currently selected in the radial menu if that type has any left.
[ ] Fire with the holding hand's trigger: spawn a pooled bolt, simple
    ballistic flight (manual integration or Rigidbody), fire sound,
    haptics. Decide on a small aiming aid (e.g. a faint sight pin on the
    crossbow).
[ ] Bolt base class + subclasses:
    [ ] Water bolt: hit a LightSource's flame collider to extinguish it
        (linked shadow volume goes dark). Small splash noise.
    [ ] Noisemaker bolt: sticks where it lands and emits repeated loud
        noise events for N seconds - guards investigate.
    [ ] Rope bolt: only sticks into surfaces tagged RopeTarget (wood); spawns
        a ClimbableRope hanging down to the ground/max length. Bounces
        off anything else.
[ ] Bolt pickups in the level (placed ammo) that add to inventory counts.
Lockpicking:
[ ] Lock component on doors/chests: pin count (2-3), randomised sweet-spot
    angle per pin, tolerance.
[ ] Insert: equip the lockpick and bring its tip into the keyhole trigger.
    The pick snaps to the keyhole visually, like climbing snaps hands.
[ ] Rotate the wrist (roll angle relative to the insertion angle) to search.
    Haptic intensity rises as you near the sweet spot; hold still in it
    for ~0.5s to set that pin (click sound + strong pulse). Pulling out
    resets the current pin (or all pins - tune).
[ ] Quiet picking noise events while working the lock.
[ ] Unlock: door becomes openable / chest lid opens.
[ ] Debug (Scripts/Interaction/Debug): show the current pin, the current
    angle vs the sweet spot.


Phase 6 - Guard AI (AI namespace)
---------------------------------
Setup:
[ ] Install/confirm the AI Navigation package; NavMeshSurface on the level.
[ ] Guard prefab: placeholder humanoid, NavMeshAgent, Animator, head
    collider (GuardHead layer), eye transform, capsule body collider.
Perception:
[ ] Vision: cone angle + range, checked on a staggered timer (e.g. 5-10Hz,
    offset per guard), LOS raycasts to 2-3 points on the player (head,
    chest, feet). Detection rate scales with player Visibility (from shadow
    volumes), distance, stance and movement. In full shadow the player is
    only seen at very close range.
[ ] Detection meter per guard (0-1) that rises/decays; thresholds drive
    state transitions.
[ ] Hearing: register with NoiseSystem; ignore noises outside range
    (optionally attenuate through a NoiseOccluder layer); louder noise =
    more suspicion.
[ ] Body discovery: seeing a KO'd guard in a lit area jumps to Search at the
    body and raises the whole level's alert level (for the slice: those
    guards search longer).
Behaviour (explicit state machine - keep it readable and debuggable):
[ ] Patrol: waypoint routes (PatrolRoute component with ordered points +
    optional wait/look-around time at each).
[ ] Suspicious: stop, turn towards the stimulus, "huh?" bark; escalate or
    return to patrol.
[ ] Search/Investigate: walk to the last known position, then pick a few
    nearby NavMesh points to check, with a timeout before giving up.
[ ] Chase: run to the player's live position while seen, last known when
    lost; drop back to Search when lost for N seconds.
[ ] Catch: within catch range while chasing, trigger GameState Caught.
[ ] Knocked out: disable perception/agent; the body becomes draggable.
    KO'd guards stay down for the whole slice.
[ ] Return to patrol after search, resuming the nearest waypoint.
Body dragging:
[ ] KO'd guard has a grab handle (collar/shoulder). The player grabs it and
    the body follows the hand along the ground (kinematic follow with
    ground snapping, or ragdoll with a joint to the hand - start with
    kinematic, it's cheaper and more predictable on Quest). Dragging
    slows the player and makes some noise on loud surfaces.
Audio feedback:
[ ] Placeholder barks per state transition (suspicious, searching, gave up,
    spotted, found body) - these are how the player reads AI state.
Debug (Scripts/AI/Debug):
[ ] Gizmos: vision cones, hearing radius, patrol routes, last-known
    position, current state label and detection meter above each guard.
Performance:
[ ] Budget: ~4-6 guards in the slice. Stagger perception, avoid
    allocations in state updates, and animator culling mode = cull
    completely when offscreen.

Phase 8 - Level: the docks warehouse
------------------------------------
Design (on paper first):
[ ] Layout sketch with a critical path and at least one alternate route per
    area. Each beat below should teach or test one mechanic, roughly in
    this order:
    1. Start: dockside at night, dark. Crouch and move quietly (wood dock
       vs metal ramp teaches surface noise).
    2. Yard: one patrolling guard, crates, shadow volumes between lamps.
       Teaches reading light/dark and patrol timing.
    3. Torch-lit gate: extinguish a torch with a water bolt to cross.
    4. Climb: ledge climb + mantle onto crates, a ladder up to a
       catwalk/roof.
    5. Rope bolt: a wooden beam high on the warehouse wall gives an
       alternate rooftop route.
    6. Warehouse interior: two guards on crossing patrols, catwalks
       overhead, loud metal floor below. Noisemaker bolt / thrown bottle to
       pull a guard off a doorway.
    7. Takedown: a lone guard facing away in a dead end - blackjack, then
       drag the body into shadow (body-discovery teaches the hiding
       reason).
    8. Office: locked door (lockpick) and a locked chest/safe with the
       objective item. Loot scattered around (coins, goblets) for a
       loot total.
    9. Escape: back out to a boat/exit zone, a guard now searching near
       the route in.
[ ] Loot target and bolt counts: enough bolts to solve each beat with a
    small spare; tune after playtesting.
Greybox build:
[ ] Block out in ProBuilder at true VR scale (door heights 2.1m, ceilings,
    catwalk rail heights, ledge heights tested at 1.2-2m).
[ ] Tag surfaces (SurfaceType), RopeTarget beams, ClimbableEdges, ladders.
[ ] Place ShadowVolumes, LightSources and their links.
[ ] Bake the NavMesh; add NavMesh links/obstacles for doors; verify guards
    can't path onto player-only routes (catwalks/roofs).
[ ] Place guards + PatrolRoutes, loot, bolt pickups, objective, exit zone,
    player start.
Lighting (Quest-conscious):
[ ] Baked lighting with light probes for the static environment; torches
    as a small number of realtime/mixed lights (baked lights can't be
    turned off by a water bolt). Keep realtime lights per view low and
    ranges short.
[ ] Make sure visible light roughly matches the shadow volumes - the player
    must be able to trust what they see.
[ ] Occlusion culling bake; split the level into chunks that cull cleanly.
Audio (placeholder):
[ ] Ambient bed (water lapping, distant bells, warehouse hum), footsteps per
    surface, door creaks, impacts, crossbow cock/fire, bolt effects,
    lockpick clicks, loot pickup, guard barks, alert/chase stinger.


Phase 9 - Game loop, feedback and slice polish
----------------------------------------------
[ ] Level start: fade in at the dock, brief objective on the wrist ("Steal
    the ledger from the warehouse office. Escape by boat.").
[ ] Caught: guard catch -> stinger -> fade -> reload at start.
[ ] Win: objective item in the exit zone -> fade -> simple "Mission
    complete - loot X / Y" world-space panel -> restart on button.
[ ] Haptics pass: pulses for grabs, climbing grips, lockpick, crossbow
    cock/fire, blackjack hit, loot pickup (none for footsteps).
[ ] Comfort pass: vignette while sprinting/jumping/falling (optional), snap/smooth
    turn works everywhere including while climbing.
[ ] Playtest checklist (in-headset, PCVR then Quest 3):
    [ ] Every beat 1-9 completable using its intended mechanic.
    [ ] Every beat completable via at least one alternate approach.
    [ ] Guards never get stuck; they always return to patrol.
    [ ] Caught -> restart and win -> restart both work repeatedly.
    [ ] Both hands can equip and use every tool.


Phase 10 - Quest 3 performance pass
-----------------------------------
[ ] First standalone build (the baseline deferred from Phase 0); profile
    with the Unity Profiler + OVR Metrics Tool.
    Target a stable 72Hz minimum (90Hz stretch).
[ ] Rendering: draw call/batch count, SRP Batcher compatibility, MSAA vs
    cost, shadows (likely off for realtime lights), foveation, render
    scale.
[ ] CPU: zero per-frame GC allocations in gameplay code, perception
    staggering verified, Animator culling, physics layer matrix trimmed,

Milestones
----------
M1  Movement complete        Phases 0-1  (all traversal in the test scene)
M2  Stealth core             Phase 2     (visibility, noise, fail/win state)
M3  Hands on everything      Phases 3-5  (grab, inventory, all tools)
M4  Guards alive             Phases 6-7  (full AI loop with animation)
M5  Playable slice           Phases 8-9  (the level, start to finish)
M6  Quest-ready slice        Phase 10    (standalone at target frame rate)

Recommended: build a small dedicated test scene per milestone (like the
existing CharacterController test scene) so each system is proven in
isolation before it goes into the level.
