TeaLeaf Development Roadmap - Vertical Slice
============================================

Goal: a single greybox level (warehouse/docks) that runs in Play Mode and
showcases every core stealth mechanic end to end - sneak in, steal the
objective item, escape - with a fail/restart loop when caught. No settings
menu, main menu, save system or final art required.

Written 2026-09-26. Tick items off as [x] and log details in DEVLOG.txt.
[-] marks an item deferred to a later phase (the item says where).


Vertical slice feature list (agreed scope)
------------------------------------------
Movement:     walk, smooth/snap turn, gravity, crouch (done), sprint, jump,
              ledge climbing (done), mantling,
              ladders, rope climbing.
Visibility:   worked out from the level's geometry - moonlight, shadowed
              wherever something stands between the player and the moon,
              plus torches and lamps within their range. Extinguishing a
              torch darkens what it lit. Wrist-mounted visibility gem for
              feedback.
Noise:        footsteps by surface type (scaled by sprint/walk/crouch),
              thrown/dropped physics objects, doors and other interactions.
Guard AI:     patrol, suspicion, search, chase, catch (= fail + restart).
              Knockout state. Guards react to finding KO'd bodies.
Tools:        blackjack takedown, hand crossbow (either hand, physically
              cocked) with water / noisemaker / rope bolts, two-handed
              lockpicking on a large copy of the lock (one pick turns in
              stages, the other searches for each pin by feel).
Inventory:    wrist radial menu to select tools/bolt types; loot pickup and
              pocketing with a running loot total.
Bodies:       grab and drag KO'd guards to hide them.
Throwing:     two ways, both kept. Aimed (fine control) - hold an object,
              hold that hand's trigger for a trajectory arc, release the
              trigger to throw (short hand launch animation). Physical -
              move the hand and let go of grip, and the object leaves with
              the hand's movement.
Hands:        physical hands - the visual hand model collides with the world
              and stops at walls/props instead of passing through, then
              catches back up to the real controller position (Half-Life:
              Alyx / Thief VR style).
Art:          greybox (ProBuilder/primitives) for environment and props.
              Placeholder humanoid + Mixamo animations for guards. Existing
              real hand models with finger animation/grip poses.


Performance rules for everything built from here (added 2026-10-07)
-------------------------------------------------------------------
Quest 3 standalone is the real target, and the cheap time to meet it is
while each thing is built, not in Phase 10. Every phase below follows
these; the short form is in the root CLAUDE.md ("Performance rules").
The tasks they lead to are in Phases 6, 8 and 10.
- Pixels are the tightest budget (two eyes, high resolution): no
  full-screen effects, no parallax or other many-sample shaders on
  surfaces that fill the view, as little see-through overdraw as
  possible.
- Light is baked where it can be; realtime lights are few, short-ranged
  and cast no realtime shadows of their own.
- Level geometry that never moves is marked Static and shares a small
  number of materials, so it batches, bakes and occlusion-culls.
- Depth the player gets close to is modelled; normal maps are for fine
  detail only.
- Level layout does the culling: bent approaches and doors break long
  sightlines, backed by an occlusion bake.
- Anything costly on the CPU (AI senses, pathfinding, light sampling,
  sound paths) runs a few times a second, staggered, never every frame -
  and less often again when far away or unseen.
- Nothing is created or destroyed during play: pool it.
- Tricks kept in reserve, to try only if profiling asks: light distance
  haze with nearer cull distances for small props, application
  spacewarp, impostors.

Physical hands (Player namespace) - a core concept, moved here from
Phase 3 (2026-09-27). Built as part of Phase 1, since grabbing, tools
and climbing all sit on top of where the visual hand ends up.
Claude to guide this step by step, starting with a comparison of the most
performant approaches for Quest 3 before any code is written:
[x] Approach comparison (2026-09-27). Chose a KINEMATIC SWEEP - no
    Rigidbody: each frame, in PlayerController's tick order (Update, at
    display rate), sweep a hand capsule from the visual hand's last pose
    towards the controller, stop at hits and slide along them
    (collide-and-slide, a few iterations, skin width), then depenetrate
    with an overlap + Physics.ComputePenetration (non-alloc). Rejected a
    velocity-driven Rigidbody hand: runs at the physics rate (needs a
    raised fixed timestep for all physics or interpolation lag), costs
    more on Quest, jitter-prone, and needs teleport special cases for snap
    turn/mantle/crouch since the rig moves in Update. Its one real win -
    pushing props for free - can be approximated later (small impulse on
    contact) and grabbing is custom anyway. Rejected a joint-driven body
    (same trade-offs, more tuning); a kinematic MovePosition body can't be
    stopped by static geometry at all.
    Design notes: one palm-to-fingertips capsule per hand to start (finger
    capsules only if needed - each shape is another sweep). While the path
    is clear the visual stays a child of the controller (keeps the
    Tracked Pose Driver's before-render update, zero added latency); while
    in contact it's detached and placed by code, like HandVisualSnap.
    Snap poses take priority; this becomes one hand-visual owner per hand.
    Hand rays from the visual hand. Ticks after Move()/turning, in
    PlayerHandVisuals.Tick() (step 1).
    Build steps: 1. one hand-visual owner, 2. sweep + slide, 3. depenetration
    + rotation, 4. elastic band, 5. hand rays from the visual, 6. test area
    + profiling.
[x] Step 1 - one owner per hand visual: new PlayerHandVisuals (on Hands)

Behaviour (explicit state machine - keep it readable and debuggable):
[ ] Patrol: waypoint routes (PatrolRoute component with ordered points +
    optional wait/look-around time at each).
[ ] Suspicious: stop, turn towards the stimulus, "huh?" bark; escalate or
    return to patrol.
[ ] Search/Investigate: walk to the last known position, then pick a few
    nearby NavMesh points to check, with a timeout before giving up.
[ ] Chase: run to the player's live position while seen, last known when
    lost; drop back to Search when lost for N seconds.
[ ] Catch: within catch range while chasing, trigger GameState Caught.
[ ] Knocked out: disable perception/agent; the body becomes draggable.
    KO'd guards stay down for the whole slice.
[ ] Return to patrol after search, resuming the nearest waypoint.
Body dragging:
[ ] KO'd guard has a grab handle (collar/shoulder). The player grabs it and
    the body follows the hand along the ground (kinematic follow with
    ground snapping, or ragdoll with a joint to the hand - start with
    kinematic, it's cheaper and more predictable on Quest). Dragging
    slows the player and makes some noise on loud surfaces.

[ ] Voice lines that don't repeat (added 2026-10-07). Guards draw from

    level never hears the same line twice - and a line isn't played again
    until every other line in its pool has been used. Barks above use
    this too, and so does idle chatter: now and then a guard on a normal
    patrol says something to himself.
    [ ] Voice line pool (Core, beside SoundCue, which picks a clip at
        random and so can repeat): one pool per kind of line (idle
        mutter, suspicious, searching, gave up, spotted, found body),
        each a long list of clips. Lightweight: a shuffled order of clip
        numbers and a place in it - take the next one each time; when
        the list runs out, shuffle again, making sure the new first line
        isn't the one just played. Built once, nothing allocated per
        line.
    [ ] Shared and lasting: one record per pool for all guards with that
        voice, so two guards don't say the same line, and kept for the whole play
        session - a level restart (being caught) must not start the
        lines over. So it lives outside the scene, and isn't saved to
        disk.
    [ ] Played through SoundPlayer like any other sound (rooms and
        portals, muffling), from the guard's head. One line at a time
        per guard; a state bark cuts off an idle mutter.
    [ ] Idle chatter: on patrol only, at a random interval with a long
        minimum gap, and not while another guard nearby is talking.
    [x] Decided 2026-10-07: several guard voices. Each voice has its own
        set of pools (one per kind of line), each guard is given a voice
        and keeps it, and "used" is tracked per voice's pool - so guards
        sharing a voice still don't repeat each other.
    [x] Decided 2026-10-07: other guards don't react to idle chatter -
        a spoken line is sound only, not a noise event.
    [ ] Later, maybe: conversations between two guards (a set of lines
        played in turn between two voices). Not planned for the slice,
        but keep the pool usable for it: a conversation would be one
        entry that isn't repeated, the same as a single line.
    [ ] Placeholder lines to prove the system; the large pools are a
        recording job - list the lines wanted per pool, and how many.
Debug (Scripts/AI/Debug):
[ ] Gizmos: vision cones, hearing radius, patrol routes, last-known
    position, current state label and detection meter above each guard.
Performance:
[ ] Budget: ~4-6 guards in the slice. Stagger perception, avoid
    allocations in state updates, and animator culling mode = cull
    completely when offscreen.
[ ] Guards far from the player or out of sight think less often (added

Phase 8 - Level: the docks warehouse
------------------------------------
[x] A first building made the way level buildings could be (2026-10-09,
    ahead of this phase, at the maintainer's request): TeaLeaf > Build
    Smithy makes a half-timbered blacksmith's house from code - one
    mesh per material (six draw calls), textures painted by the script
    and saved as PNGs, Static with mesh colliders, hollow, and about 35
    ledges, window sills, ridges and ladders to climb.
[ ] Try the smithy in the headset: how it looks, whether every ledge

Design (on paper first):
[ ] Layout sketch with a critical path and at least one alternate route per
    area. Each beat below should teach or test one mechanic, roughly in
    this order:
    1. Start: dockside at night, dark. Crouch and move quietly (wood dock
       vs metal ramp teaches surface noise).
    2. Yard: one patrolling guard, crates, shadows between the lamps.
       Teaches reading light/dark and patrol timing.
    3. Torch-lit gate: extinguish a torch with a water bolt to cross.
    4. Climb: ledge climb + mantle onto crates, a ladder up to a
       catwalk/roof.
    5. Rope bolt: a wooden beam high on the warehouse wall gives an
       alternate rooftop route.
    6. Warehouse interior: two guards on crossing patrols, catwalks
       overhead, loud metal floor below. Noisemaker bolt / thrown bottle to
       pull a guard off a doorway.
    7. Takedown: a lone guard facing away in a dead end - blackjack, then
       drag the body into shadow (body-discovery teaches the hiding
       reason).
    8. Office: locked door (lockpick) and a locked chest/safe with the
       objective item. Loot scattered around (coins, goblets) for a
       loot total.
    9. Escape: back out to a boat/exit zone, a guard now searching near
       the route in.
[ ] Loot target and bolt counts: enough bolts to solve each beat with a
    small spare; tune after playtesting.
[ ] Lay it out so the level culls itself (added 2026-10-07): no long
    straight views across the whole site - bent approaches, the yard
    wall, the warehouse's own walls and doors between areas, so that
    from any spot only one or two areas can be seen. The interior and
    the docks should rarely be on screen together.
Greybox build:
[ ] Block out in ProBuilder at true VR scale (door heights 2.1m, ceilings,
    catwalk rail heights, ledge heights tested at 1.2-2m).
[ ] Mark everything that never moves Static (added 2026-10-07; nothing
    in the scene is yet, and the test-area builders don't set it), on
    the Environment layer, with a small number of shared materials -
    one material and one colour-swatch texture can cover the greybox.
    Box/capsule colliders where they fit; mesh colliders only where the
    shape needs one.
[ ] Small props (bottles, coins, crates) cast no realtime shadows.
    They're on Interactable, not Environment, so that layer can be
    given a nearer cull distance than walls if profiling asks for it.
[ ] Tag surfaces (SurfaceType), RopeTarget beams, ClimbableEdges, ladders.
[ ] Place the LightSources, each with its visible Unity light (no shadow
    volumes: visibility is worked out from the geometry, 2026-10-04).
[ ] Bake the NavMesh; add NavMesh links/obstacles for doors; verify guards
    can't path onto player-only routes (catwalks/roofs).
[ ] Place guards + PatrolRoutes, loot, bolt pickups, objective, exit zone,
    player start.
Lighting (Quest-conscious):
[ ] Baked lighting with light probes for the static environment; torches
    as a small number of realtime/mixed lights (baked lights can't be
    turned off by a water bolt). Keep realtime lights per view low and
    ranges short.
    [ ] Decide how the moon is lit (added 2026-10-07). It never moves,
        so its light and shadows on the level can be baked. To try
        first: the Directional Light as Mixed, lighting mode
        Subtractive or Shadowmask - the level's shadows come from the
        lightmap, and only moving things (guards, props, hands) are
        drawn into a small, short-distance shadow map. Fully realtime,
        as now, redraws the whole level into the shadow map each frame.
    [ ] Decide how torches are lit (added 2026-10-07). The problem: a
        realtime point light with no shadows shines through walls,
        while the gameplay light (LightSource) is blocked by them - and
        point light shadow maps cost six views each, off on Quest. To
        try first: torches as Mixed lights in Shadowmask mode with
        indirect light at zero - the light itself stays realtime, so a
        water bolt can still put it out, but its shadows from the level
        are baked, so walls block it for no shadow map. At most four
        such lights may overlap at any one spot.
    [ ] No more than four lights besides the moon reach any one object
        on Quest (URP Forward's limit; extra ones are dropped and pop).
        Keep torch ranges short and don't merge the level into a few
        huge meshes - or test Forward+ on the device.
    [ ] Light probes along every route the player, guards and props
        use; one baked reflection probe, or none.
[ ] Make sure visible light matches the gameplay light (SceneLight) -
    the player must be able to trust what they see. Every mesh that
    casts a shadow has a collider on Environment or Interactable.
[ ] Occlusion culling bake; split the level into chunks that cull cleanly.
[ ] Set the camera's far clip plane to a little more than the longest
    view in the level (the sky doesn't depend on it). Brought in from
    1000m to 200m on 2026-10-07 as a first step.
[ ] If profiling asks for it: light distance haze (URP's built-in fog,
    not a depth-based effect) with nearer cull distances for small
    props. It needs the sky to fade into the same haze at the horizon,
    and must stay thin enough to read lit and dark areas from afar.

Phase 10 - Quest 3 performance pass
-----------------------------------
[ ] First standalone build (the baseline deferred from Phase 0); profile
    with the Unity Profiler + OVR Metrics Tool. The OpenXR "Meta Quest
    Support" feature is still off for Android (seen 2026-10-07) - turn
    it on first.
    Target a stable 72Hz minimum (90Hz stretch).
[ ] Rendering: draw call/batch count, SRP Batcher compatibility, MSAA vs
    cost, shadows (likely off for realtime lights), foveation, render
    scale.
    Found in the 2026-10-07 settings review (Mobile_RPAsset is what a
    Quest build uses), to settle on the device:
    [x] HDR was on with no post-processing to use it. Turned off in
        Mobile_RPAsset 2026-10-07 (PC keeps it). Not yet seen on the
        device.
    [ ] MSAA is off and render scale is 0.8. On Quest's GPU 4x MSAA is
        cheap and matters a lot in VR; try 4x at scale 1.0 and come
        down only if the frame time says so.
    [ ] Foveated rendering. Set up 2026-10-07, untested: the OpenXR
        feature is enabled for Android with the SRP Foveation API, and
        Core.FoveatedRendering asks for level 0.5 when a Quest build
        starts. Left: check it on the device and tune the level (watch
        the stars at the edges of the view).
    [ ] Dynamic resolution as the safety net for heavy moments.
    [ ] Environment and prop materials are URP Lit (full PBR). Compare
        Simple Lit and Baked Lit on the device once lighting is baked.
    [ ] The procedural surface shaders (TeaLeaf/Cobblestone and
        TeaLeaf/BrickWall, added 2026-10-08) work their pattern out per
        pixel, on surfaces that fill the view. Profile them on the
        device, with and without Dirt and Parallax; the cobbles' 5x5
        search is the heavy one. If they cost too much, bake each
        pattern into textures at level load (as the moon's face is) and
        keep the same material settings. Both also need a Meta pass
        before a lightmap bake can see their colours (Phase 8).
    [ ] Main light shadows: distance 50m at 1024 with one cascade is
        both costly and blurry; with baked level shadows (Phase 8) it
        only has to cover moving things near the player - try 10-15m.
    [ ] Keep off for Quest: post-processing, depth and opaque textures,
        soft shadows, additional light shadows (all off today).
    [ ] Textures: ASTC, sensible maximum sizes, mipmaps on anything in
        the world.
    [ ] Application spacewarp only as a last resort (it has artefacts
        on fast hands and thin shapes).
[ ] CPU: zero per-frame GC allocations in gameplay code, perception
    staggering verified, Animator culling, physics layer matrix trimmed,
    fixed timestep appropriate.
    [x] Props are smoothed between physics steps (50Hz physics, 72-90Hz
        headset) by Rigidbody interpolation, not a faster physics rate:
        Grabbable has set it on every drop and throw since 2026-10-07,
        and the test props now start with it on too.
[ ] Audio: every clip's import settings read as Decompress On Load
    with Preload Audio Data off (seen in the .meta files 2026-10-07;
    check in the Inspector). If so, each clip is decoded on the main
    thread the first time it plays - a hitch on the first footstep on
    each surface. Turn preloading on for short sounds; long ambience
    loops should stream or stay compressed in memory.
[ ] Object pooling for bolts, impact/noise VFX and audio sources.
[ ] Record final numbers in DEVLOG.txt as the post-slice baseline.
