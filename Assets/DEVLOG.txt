TeaLeaf Development Log
========================

This file tracks development progress on TeaLeaf, a Thief-style VR stealth game
(Unity, OpenXR + XR Interaction Toolkit). Newest updates are at the top.

- Hand snap poses, step 2 of 3 (Phase 1). A general way for any grab
  target to say where a hand visual goes and how it's posed:
  HandPose (enum of finger poses), HandSnapPose (readonly struct: world
  position, rotation, pose) and IHandSnapTarget (GetSnapPose(isLeftHand,
  grabPoint)), all in Interaction. The target works out a model-agnostic
  "grip frame"; a shared HandSnapProfile ScriptableObject then applies
  per-hand position/rotation offsets (per hand because the right visual is
  mirrored). Chose a shared asset over per-edge fields so the offsets are
  tuned once for every ledge. ClimbableEdge implements it: the ray hit is
  moved to the box's top-front line in local space (clamped to the edge's
  length), facing into the wall. New convention: edge local X along the
  edge, +Y up, +Z out from the wall.
  HandVisualSnap (plain C# class, one per hand, owned by PlayerClimbing for
  now) blends the visual to the snap pose over 0.08s with SmoothStep and
  back on release, and skips touching the transform entirely at rest.
  Found while doing this: the old pinning ran inside PlayerClimbing.Tick(),
  before turning and Move() - since the visuals are children of the rig,
  every pinned hand was dragged off by that frame's movement until the next
  frame. Visuals are now placed in PlayerClimbing.TickHandVisuals(), a new
  last step (9) in PlayerController.Update(). Finger pose is carried in the
  snap pose but not played yet (step 3).
- Bug: snapping worked in headset, but a snapped hand still moved slightly
  with controller rotation/movement. Cause: the hands' Tracked Pose Drivers
  use "Update And Before Render" (m_UpdateType 0), so just before rendering
  - after all our Update() code - they move the controller again with
  fresher tracking data, dragging any child visual with it. Setting the
  pose later can't beat that reliably (before-render callback order isn't
  guaranteed). Fix: HandVisualSnap detaches the visual (SetParent(null,
  true)) on snap and re-attaches it to the controller when the release
  blend ends. Parented to the scene root rather than the ledge, because the
  ledges are non-uniformly scaled cubes and a rotated child under one would
  shear. Lesson: anything that must stay world-fixed can't be a child of a
  tracked transform. Verified in headset - snapped hands now stay dead
  still on the ledge. Step 2 done.
- Committed as two commits: MovementState (code only), then the climb
  grab + snap poses together with the scene and all doc updates, since
  those files mixed changes from both.
- Hand snap finger pose, step 3 of 3 - code side (Phase 1). Chose a new
  "Snap Pose" override layer on top of the hand controller over forcing
  TriggerCurl/GripCurl to 1 (that only gives a closed fist, not fingers
  hooked over a lip, and every future pose would need more parameters).
  The layer's states are named after HandPose values, hashed once from the
  enum names, so a new pose is an enum value + state + clip with no new
  code. Its weight is HandVisualSnap's new Weight (the eased snap blend),
  so the fingers close exactly as the hand lands and open as it leaves -
  one source of timing. Removed PlayerHandAnimation's HandState enum:
  every non-input pose is now a snap pose, so the snap weight already says
  who owns the fingers; the input layers always run underneath.
  PlayerHandAnimation.Tick() moved to the end of the frame (after
  TickHandVisuals) so it reads this frame's weight - free, since Animators
  evaluate after all Update() calls anyway. Updated roadmap items that
  mentioned HandState.
- Bug: with the Snap Pose layer + LedgeGrip clip in place, the index
  finger hooked correctly but middle/ring/pinky looked like the grip
  animation. The clip only keyed joint 2 of each finger, and a layer only
  overrides the bones its clip keys - joints 1 and 3 kept the Grip layer's
  curl, which is fully closed because grip is held to climb (the index
  only looked right because the trigger wasn't pulled). Fix: key joints 1,
  2 and 3 of every finger in the snap clip. Lesson (corrects my earlier
  note): Write Defaults does not reset unkeyed bones on this rig, which is
  the same behaviour that lets Base and Grip share the hand without masks.
  Verified in headset after keying joints 1-3: all four fingers hook over
  the lip and ignore grip/trigger while snapped. Step 3 done.
- Jump (Phase 1). Right B via the
  project-wide Player/Jump action; its XR binding was
  <XRController>/secondaryButton (B or Y on either hand), narrowed to
  {RightHand}/{SecondaryButton}. PlayerInputXR.JumpPressed. Launch speed
  derived from a tunable jumpHeight (0.5m): u = sqrt(2 * h * -g).
  Momentum: HandleMovement() now keeps one _horizontalVelocity - set from
  the stick while grounded (same as before), kept while airborne, so
  running jumps go further and walking off an edge keeps speed. Air
  control (decided: light) nudges it at 3 m/s^2 towards the stick; a
  centred stick drags it at 0.5 m/s^2. Climb release momentum will seed
  the same value later.
  Collision response: PlayerController now passes Move()'s CollisionFlags
  to TickState(). Above zeroes upward velocity (a jump into a low ceiling
  bonks instead of sticking) - chosen over a pre-jump clearance check;
  Sides while airborne replaces momentum with the velocity actually
  applied, so walls redirect it along themselves rather than letting it
  keep pushing in.
  Crouch (decided): jump while crouched just stands up, and a jump waits
  until the capsule is fully standing. Coyote time 0.1s, jump buffer
  0.15s, a _hasJumped flag stops coyote time allowing a second jump while
  rising, and MovementState goes Airborne immediately on a jump rather
  than after the grace period. Climb start clears horizontal velocity and
  any buffered jump. New Landed event (Action<float>, fall speed) raised
  on grounding after Airborne, for landing noise and haptics later. This
  also puts PlayerLocomotion's previously unused "using System;" to use.
  MovementStateDebug now also logs Landed with its fall speed. Verified
  in headset - jump done.
- Climb release momentum (Phase 1), built - awaiting headset test.
  PlayerClimbing records the movement the CharacterController actually
  applied each climbing frame (in ReportAppliedMovement - real movement,
  so a climb pushing into a wall doesn't launch you into it) into a fixed
  ring buffer of the last 5 frames, allocated once in Awake. Averaged as
  total distance / total time rather than averaging per-frame velocities,
  so uneven frame times are weighted correctly. On the frame the climb
  ends it becomes ReleaseVelocity: x launchMultiplier (1), clamped to
  maxLaunchSpeed (5 m/s), zeroed below minLaunchSpeed (0.3 m/s) so hand
  jitter on a gentle let-go is a clean drop. Samples reset on climb start
  but not on a hand-off (one continuous climb). PlayerLocomotion.
  TickMovement() now takes the release velocity and, on the climb-end
  frame, seeds _verticalVelocity and _horizontalVelocity with it - the
  same values a jump sets, so air control, drag, gravity and the
  wall/ceiling collision response all apply with no extra code. Decided:
  jumps and releases share the same air drag. MovementStateDebug logs the
  release velocity when a climb ends (optional PlayerClimbing reference).
- Climb release: momentum works in headset, but there's a brief stutter
  at the moment of release before the momentum kicks in. Traced the code:
  no frame has zero movement (climb movement stops and momentum starts in
  the same frame), so it's a speed discontinuity, not a gap. Two
  candidates: (1) the hand slows while the fingers open - the climb only
  ends at grip < 0.5, so the body follows a braking hand, then the 5-frame
  average kicks it forward again; (2) the average lags a still-
  accelerating push, so speed drops at release. They need different fixes
  (a release hysteresis threshold vs a better at-release velocity
  estimate), so added ClimbReleaseDebug (Player/Debug) to log real player
  velocity and both grips for the frames around each release before
  choosing.
- ClimbReleaseDebug results (4 push-offs): speed peaks at 5-7 m/s, then
  drops over 2 frames to ~1.2-3 m/s while grip is still held (often 1.00),
  then jumps back to 3-4.7 m/s on release - brake-then-kick. So it's
  cause (1), but from the arm stopping at full extension before letting
  go, not from the grip opening slowly (the grip often goes 1.00 -> 0 in
  one frame). Lesson: while gripping, the body is locked 1:1 to the hand,
  so that braking has already been shown; any launch faster than the last
  climbing frame's velocity has to be a kick, whatever the estimator.
  Decided: seamless - velocitySampleFrames = 1, so the launch continues
  at exactly the last frame's velocity. Big launches now need letting go
  mid-push, like real life. Rejected: keeping the averaged launch and
  easing into it over ~0.1s (removes the jerk but keeps the
  brake-then-surge). launchMultiplier must stay 1 and releases above
  maxLaunchSpeed (5) still slow down suddenly - both noted on the fields.
- Climb release momentum REMOVED. The seamless version didn't feel good
  in headset either, so the whole mechanism came out and letting go of a
  climb drops from rest again, as before. Reverted PlayerClimbing,
  PlayerLocomotion, PlayerController and MovementStateDebug to the last
  commit (none of it had been committed), deleted ClimbReleaseDebug, and
  hand-removed its component and the four release fields from Main.unity -
  not a whole-file revert, because the scene also held two ledges
  re-oriented to the ClimbableEdge convention that needed keeping.
  Roadmap item marked [-] removed, CLAUDE.md records it as a design
  decision so it isn't re-suggested. Lesson: with the body locked 1:1 to a
  gripping hand, "launch on release" has no good version - averaged
  launches stutter, seamless ones barely launch. A future push-off would
  need a different model (e.g. launching while still gripping), not a
  better velocity estimate.
- Roadmap change: rewrote the Mantling item to the agreed design. Mantle
  is triggered, not automatic: when gripping a mantleable (always
  horizontal) ClimbableEdge with the head pulled up near its top, and the
  destination is clear, a small white head-locked arrow appears; pushing
  up on either thumbstick starts it. It's quick, overrides all other
  locomotion, can't be cancelled, and always lands a fixed horizontal
  offset inward from the lip. Decided: arrow needs gripping + pulled up
  (not just gripping, and not standing at the ledge); only-crouch-height
  space auto-crouches, no space = no arrow.
- Mantling step 1 of 2 - detection + arrow (built, awaiting headset test).
  ClimbableEdge gets isMantleable, InwardDirection, and ClosestLipPoint()
  (the lip-projection maths pulled out of GetSnapPose so snapping and
  mantling share it). PlayerClimbing exposes Left/RightGrabbedEdge;
  PlayerLocomotion exposes StandingHeight/CrouchHeight. New PlayerMantling
  (Player root, ticked after climbing) checks, cheapest first: gripping a
  mantleable edge -> head >= ledge top - 0.3m -> floor found by a short
  downward ray 0.4m in from the lip -> CheckCapsule for standing, else
  crouch height. The landing height comes from that ray rather than the
  edge box's top face, since the box only marks the lip and may sit a
  little above/below the real surface (which would make the capsule check
  overlap the floor and never allow a mantle). New MantleIndicator (child
  of Main Camera, so head-locked for free): runtime-built arrow mesh on
  UI/Default with unity_GUIZTestMode = Always - draws through walls, and
  UI/Default already handles single-pass stereo, which a quick custom
  shader might not (one-eye rendering). A scene gizmo shows the landing
  capsule green/yellow/red.
- Design change (before testing): mantling simplified. Each mantleable
  ClimbableEdge now carries its own designer-set data instead of
  PlayerMantling working it out: a mantleEndsCrouched switch, and a
  mantlePoint Vector3 - where the feet always land, wherever along the
  ledge the mantle started. The point is relative to the edge's origin in
  real metres along its axes: MantlePointWorld = position + rotation *
  point, deliberately not TransformPoint(), because ledges are stretched
  cubes (e.g. 3.8 x 0.2 x 0.37) and scale would distort the offset. Its
  default is computed from the box (top face, 0.4m in from the lip,
  centred along the edge) in Reset() and a "Reset Mantle Point" context
  menu (with Undo.RecordObject so the edit is saved); a selected-edge
  gizmo shows it. Removed from step 1: the floor ray, both CheckCapsule
  clearance checks, landingLayers, landingOffset, InwardDirection, the
  landing gizmo, and PlayerLocomotion's Standing/CrouchHeight getters.
  PlayerMantling now only checks "gripping a mantleable edge + head pulled
  up", with no physics queries, and exposes MantleEdge.
- Mantling step 1 verified in headset: the arrow shows once pulled up on a

- Ladders - design agreed (Phase 1). Shared code via a new IClimbable
  interface rather than a "Climbable" base class: no inheritance chain

2026-09-26

- Roadmap change: added a Phase 1 item (before Jump) for ray-targeted climb
  grabs. A hand will start climbing when grip is pressed while its hand
  ray/reticle is on a ClimbableEdge, instead of when its SphereCollider
  overlaps one - the climb spheres get removed. On grab the visual hand
  snaps to the edge with a defined position, rotation and a "fingers over
  the lip" pose. This snap is designed as a general concept (a hand snap
  pose that any grab target supplies, per hand) so ladders, ropes, doors,
  tools and props reuse it rather than each special-casing the hand.
  Updated the ladder/rope, hand pose, physical hands and grab pose items to
  match, and added an open decision on max grab reach (the ray is longer
  than an arm).
- MovementState (Phase 1): a single enum - Still, Walking, Sprinting,
  CrouchStill, CrouchWalking, Climbing, Airborne - on PlayerLocomotion, for
  noise/visibility/AI to read. Crouch is folded into the enum rather than
  kept as a separate flag, since crouched-still and crouched-moving need
  different noise/visibility anyway. Computed in a new TickState(), called
  by PlayerController right after Move(), because it needs the real applied
  movement (so sprinting into a wall reads as Still) and the fresh
  isGrounded. Airborne waits for a 0.15s grace period because isGrounded
  flickers on steps and slopes. Added MovementStateDebug (logs transitions)
  to verify it.
- Sprint (Phase 1). Click-to-toggle on the left stick click rather than
  hold-to-sprint, since holding a stick click while pushing that stick is
  tiring. sprintSpeed (4.5 m/s vs 3 walk) replaces moveSpeed while sprinting;
  the sprint ends when the stick returns to centre, on a second click, on
  crouch or on climb, and can't start while crouched. Exposed as
  PlayerLocomotion.IsSprinting. Verified working in headset.
- Input: found crouch was wired to XRI's "Jump" action (right A), a
  confusingly named action in the XRI sample asset. New gameplay actions now
  live in the project-wide Assets/InputSystem_Actions.inputactions (Unity 6
  creates and auto-enables it) instead: gave its Player/Sprint action an XR
  binding (left stick click - it had a placeholder "any controller trigger"
  binding) and added an XR binding for Player/Crouch (right A). Jump will use
  its Player/Jump action on right B instead of A. PlayerInputXR now enables
  every action it reads in OnEnable(), since they come from two assets
  enabled by two different things.
- Roadmap change: deferred the Phase 0 Quest 3 standalone baseline build to
  Phase 10. Development stays PCVR-first for now; Quest 3 standalone is still
  the eventual target, so the Quest-minded performance habits continue. That
  closes out Phase 0 - next up is Phase 1 (sprint first).
- Restructured the player in Main.unity: unpacked the XR Origin prefab,
  renamed PlayerRig to Player, deleted XRI's unused Locomotion object, and
  moved PlayerHandInteraction/PlayerHandAnimation onto a new Hands object
  (under Camera Offset) that now parents Left Hand/Right Hand. Body systems
  stay on the root, hand systems on Hands. Hands must stay under Camera
  Offset with an identity transform, or tracked hand poses and crouch would
  be offset. PlayerController verified working after the refactor;
  PlayerController.Reset() now finds the hand components in children.
- Added PlayerController (Phase 0 tick orchestrator). PlayerLocomotion.Update()
  had grown into two jobs - locomotion, and running every other player system
  in order - and Phase 1 was about to pile sprint, jump, mantling and ladders
  into it. PlayerController is now the only player script with an Update():
  it ticks input, body (centre + crouch), hand rays, climbing and hand
  animation in order, collects movement from PlayerLocomotion.TickMovement()
  and PlayerClimbing.FrameMovement into _frameMovement, calls Move() once,
  and reports the applied movement back to climbing. PlayerLocomotion lost
  its Update() and its references to the other systems; HandleMovement()/
  HandleGravity() now return their movement instead of writing to a shared
  field. Frame order and behaviour are unchanged. PlayerController.Reset()
  auto-fills its references when added to PlayerRig (Reset() is an
  editor-only callback, free at runtime).
- Design change: jumping is now in the project (it was previously decided
  against). Added a Jump item to Phase 1 ahead of climb release momentum,
  since both need the same horizontal air momentum in PlayerLocomotion -
  build it once for jump, then reuse it for pushing off ledges. Also added
  an Airborne movement state, landing noise (Phase 2 footsteps), jump
  cases in the test scene, and jumping to the comfort pass.
- Roadmap change: added climb release momentum to Phase 1. Letting go of a
  ledge currently drops the player with no momentum; the plan is to average
  the climb's actually-applied velocity over the last few frames and carry
  it into the fall on release (vertical into _verticalVelocity, horizontal
  into a new decaying air momentum), so pushing off a ledge launches you.
- Physics layers set up (Phase 0): Environment, Player, PlayerHands,
  Interactable, Climbable, Guard, GuardHead, Projectile (user layers 6-13),
  assigned in Main.unity. Dropped ShadowVolume and NoiseOccluder from the
  planned list - visibility will use a self-registered point-in-box check
  like ClimbableEdge (no physics), and walls on Environment can block sound.
  Collision matrix trimmed to the pairs that actually need contacts (see
  CLAUDE.md). Hand rays now only hit Environment/Interactable/Climbable, so
  walls block them and edges can no longer be highlighted through a wall.
  Learned: the collision matrix only governs contacts, triggers and
  CharacterController blocking - raycasts/overlaps ignore it and use their
  own LayerMask.
- Bug: NullReferenceException in HandRayReticle.Tick() when entering Play
  Mode before the controllers were tracked. XRI's XR Input Modality Manager
  on PlayerRig deactivates the Left/Right Controller objects in its
  OnEnable when no controller is connected yet - and PlayerRig is set up

- Roadmap change: added physical hands to the slice scope (Phase 3, before
