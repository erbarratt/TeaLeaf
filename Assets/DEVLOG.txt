TeaLeaf Development Log
========================

This file tracks development progress on TeaLeaf, a Thief-style VR stealth game
(Unity, OpenXR + Input System; XR Interaction Toolkit until 2026-09-30).
Newest updates are at the top.


2026-09-30 (after the first commit)
-----------------------------------
- Town test area (on request, before starting Phase 2): TeaLeaf > Build
  Town Test Area, a third editor builder, modelled on a reference photo of
  a two-storey Gulf mud-brick house - big shapes only. Six houses from
  BuildingSpecs round a square 35m behind the spawn: a 3.6m ground floor
  with a roof parapet, an optional tower (second storey over one end or
  the whole house) with its own parapet, an optional raised terrace with
  a 20 degree ramp for its steps, and an optional balcony with a pergola
  roof. Doors and windows are empty openings - each wall is built as the
  pieces around its openings. Inside each tower a ramp runs up the side
  wall to the first floor through a hole cut from where headroom runs
  out; a door leads out onto the lower roof. Plus four 2.4m compound
  walls and some crates. Ledges sit where a building has them, about a
  metre apart so every face climbs hand over hand to the roof: sills
  (both sides, mantled into crouched - a 1.2m window is too low to stand
  in), window hoods and roofline bands (grab only), parapets,
  balustrades, compound walls and pergolas (mantleable).
  Learned: a mantle moves the player with collision off, rising then
  moving forward, so it must land ON TOP of what it climbs (a parapet or
  balustrade top) - a landing point beyond a wall or railing would drag
  the feet through it. The player steps or drops down afterwards.
  Edge creation moved into the shared TestGeometry.Edge() (any yaw,
  landing inset, TopCentreInset()); the locomotion course uses it too.
- Mantling: new per-edge "Move Horizontally To Point" switch on
  ClimbableEdge (moveHorizontallyToPoint, default on = unchanged
  behaviour, so every existing edge is unaffected). Off, the mantle lands
  straight ahead of the player: the mantle point's height and distance
  back from the lip, but the player's own position along the edge (feet
  measured square-on, clamped to the lip's ends). Found testing the town:
  its parapets run for up to 10m, and a fixed point carried the player
  sideways to the middle. ClimbableEdge.GetMantleLanding(feet) returns
  either landing and PlayerMantling uses it; the rise-then-forward motion
  is unchanged. The selected-edge gizmo draws a landing line instead of a
  point when it's off. The town's long ledges use off; window sills keep
  the fixed point (the middle of the opening). Verified in headset.
- Roadmap: noted the switch on the Phase 1 mantle destination item and
  the town under the test scene item.
- Docs: Scripts/Player/CLAUDE.md (town builder, TestGeometry.Edge(),
  mantle landing decision), Scripts/Interaction/CLAUDE.md
  (moveHorizontallyToPoint).
- Next: Phase 2, starting with the screen fade.

  RopeGrip, appended at the end: HandSnapProfile assets store the pose as
  its number and PlayerHandAnimation uses it as an array index, so
  inserting or reordering values would silently change every profile's

  warning on every grab. New clips Hand_L_RungGrip/Hand_L_RopeGrip, shaped

  clips also pose the thumb, which nothing had animated before; it returns
  to rest on release. The rope's frame has the same shape as the ladder's

  ledge. HandVisualSnap always blended from the rest pose on the
  controller. Now Snap() records where the visual actually is (in the
  controller's space, so it still follows the real hand during the blend)
  as the blend's start; Release() resets it so a release still blends back
  onto the controller.
- Haptics (Phase 1 optional feedback). LeftHaptic/RightHaptic actions
  (PassThrough, <XRController>{Hand}/haptic - the name every OpenXR

  OpenXRInput.SendHapticImpulse. First test didn't buzz; temporary logging
  plus a second test through the older XR.InputDevice API showed both
  routes working on the next try (likely the actions weren't picked up
  before a recompile) - removed again. PlayerHandVisuals raises
  HandContactStarted on the frame a hand goes from free to touching (not
  on snapping); PlayerHaptics taps that controller (0.15 / 0.03s) with a
  0.25s per-hand cooldown so sliding over bumps doesn't buzz constantly.
  Global vibration on/off: PlayerHaptics.HapticsEnabled (serialized,
  checked once in Pulse(), so it covers every future haptic), for a later
  settings dialogue alongside smooth/snap turn. Verified through Virtual
  Desktop + SteamVR.
- Ghost hands (Phase 1 optional feedback): HandGhost, one per hand, owned
  by PlayerHandVisuals. A copy of the hand visual made at startup under
  the controller (so tracking moves it, with no code), Animator removed,
  finger bones copied from the visual while shown. Shows once the visual
  is held 3cm from the controller, hides within half that, never while
  snapped. New TeaLeaf/Ghost shader: no depth test (the real hand is
  usually inside the wall, so a depth-tested ghost would be hidden), queue

2026-09-29
----------
- Design only, no code: aimed throwing added as a slice mechanic. Instead
  of physically throwing a held object, grip holds it, holding that hand's
  trigger shows a trajectory arc, and releasing the trigger plays a short
  hand visual launch animation and throws the object along the arc.
  Distance comes from the hand's pitch with a fixed launch speed, like
  standard VR teleport arcs. The aim is accuracy (noisemakers and
  distractions need to land where intended) and avoiding how awkward
  physical throwing feels in VR (no weight, release timing, noisy hand
  velocity). Releasing grip without aiming just drops the object.
- How the design got there: the first draft aimed with the right stick
  pushed forward and threw on a button still to be chosen. That clashed
  with the right stick's snap turn and mantle (stick up), and left open
  which hand throws. Moving aim/throw to each hand's own trigger fixed
  both - either hand throws what it holds, and the sticks aren't involved.
  The triggers only curled the index finger until now, so they were free.
- Cancel: aim-at-nothing, as with teleport arcs - a hand pitched too far
  up or down, or an arc with no valid landing, turns the arc red/faded,
  and releasing the trigger then cancels. Considered and rejected
  fast-release-throws / slow-release-cancels: a tense player easing off
  the trigger would silently lose a throw, there's no feedback before
  release, and the speed threshold would differ per player. It could come
  back later as a second cancel if playtests ask. Letting go of grip while
  aiming (clashes with grip release = drop) and face-button or stick-click
  cancels (different on each hand) were also rejected.
- Roadmap: added Throwing to the feature list; in Phase 3 the physical
  throw (velocity averaged from PlayerTracking hand positions) is replaced
  by an "Aimed throwing" item, with the input/distance and cancel
  decisions ticked and the arc and launch animation still to build.
  CLAUDE.md (root slice mechanics) and Scripts/Player/CLAUDE.md (design
  decision, trigger row in the input table) updated to match.

- In-headset gizmos (Phase 1 debug item, widened on request from "the
  hand capsules" to every component with gizmos). Gizmos only show in one
  eye in VR - Unity draws them for one flat camera. New Scripts/Core/Debug
  (the first thing in Core, with its own CLAUDE.md): DebugLines draws
  line-built wireframes (line, circle, sphere, box, capsule) to either the
  Scene view's Gizmos or a list of line vertices; a component implements
  IDebugDrawable.DrawDebug(lines, detailed) once and registers with
  DebugDrawRegistry, so the Scene view and the headset always match.
  InHeadsetGizmos (on a Debug object) puts every drawable into one line
  mesh, one draw call, drawn with a new TeaLeaf/DebugLines shader (vertex
  colour, depth test as a material property for "see through walls").
  PlayerHandVisuals, ClimbableEdge, Ladder and ClimbableRope converted;
  DebugLines is now the only code calling Gizmos directly, and a root
  CLAUDE.md rule says new gizmos go through it. Chose one shared line
  mesh over the roadmap's two spheres + a cylinder per hand, so every
  system (later AI vision cones, shadow volumes) can use it.
  Learned: the mesh is rebuilt in RenderPipelineManager.
  beginContextRendering, not LateUpdate - the Tracked Pose Drivers move
  the controllers again just before rendering, so anything built earlier
  trails the hands. Also DefaultLayerGizmos: magenta outlines of colliders
  left on the Default layer (colliders only - the layer matters for
  physics; lights and groups are fine on Default). Using it, colliders
  were moved to proper layers in Main.unity.
- Bug: after a hand had been in a wall, its position sometimes jumped
  back to the controller while its rotation still eased. Cause: one
  "in contact" flag covered both, and contact only ended once the hand
  fitted at the controller's rotation - a hand free to move but not to
  turn stayed in contact, and contact movement isn't eased. Fix:
  HandPhysicalFollow holds and releases position and rotation separately,
  each with its own elastic-band ease. Then, on request, the maxSeparation
  snap-back eases too (through the wall, collision off, then waits on the
  controller until it's clear) - every return to the controller is eased.
- Ladder could be grabbed from behind, and the hand snapped on facing the
  wrong way. IHandTarget gained CanBeTargetedFrom(rayOrigin) - a C#
  default interface method returning true, so only targets that care
  override it. Ladder refuses hands behind its rung line unless
  climbableFromBack is ticked, which also flips the grip for back grabs.
  A refused ray still stops at the ladder: no reticle, no grab.
- Physical hands step 6a, test area: an editor menu (TeaLeaf > Build
  Physical Hands Test Area, Scripts/Player/Debug/Editor) builds an inside
  corner, a 2cm thin panel, a table with an Interactable crate, a pillar, a
  5cm gap (the hand is 7cm), a 45 degree slope and a round post - exact
  sizes, rebuildable, undoable. Added a PhysicalHands.Follow
  ProfilerMarker for step 6b. Everything blocked the hand with no
  tunnelling except one bug:
- Bug: the visual jittered left and right with the controller in the 5cm
  gap, more the deeper it went. Two guessed fixes didn't cure it (both
  kept, as they close real holes): crease handling in collide-and-slide
  (in a V, slide only along the line where the two surfaces meet), and a
  sweep starting against a surface now stops instead of letting the hand
  through - only the first sweep, when the push-out couldn't clear the
  hand, lets it through. Then built PhysicalHandsTrace (Player/Debug):
  logs every sweep's hit (collider, distance, normal) for colliders
  matching a name filter, enabled before Play since toggling things in the
  headset is awkward, read back from Editor.log. The trace showed the
  real cause at once: each slide carried the leftover length of the
  original move (about the controller's depth) redirected along the
  surface, so the hand slid round a block's edge and out - 6.8cm sideways
  and further from the controller than it started - then straight back
  next frame. Fix: every slide re-aims at the goal (the way to the goal,
  projected onto the surface), which can never take the hand further from
  it. Learned: after two failed guesses, instrument instead of guessing;
  and a jitter that grows with input distance points at code that moves
  by "whatever's left".
- Rope: the reticle flickered on and off while reaching for it, and it
  couldn't be grabbed once the hand touched it. Cause: the scene rope's
  grab capsule (grabRadius 0.04, and not a trigger) and its visible
  cylinder (radius 0.04, moved from Climbable to Environment in the
  Default-layer cleanup) were the same size, so rays tied between them.
  Decided: a rope has a solid Environment collider inside a larger trigger
  grab volume, and a hand INSIDE any hand target's volume can grab it -
  PlayerHandInteraction checks for that (a 1mm overlap query) before
  casting the ray, since a ray never detects a collider it starts inside.
  ClimbableRope always makes its grab capsule a trigger (the collider is
  locked in the Inspector) and warns if a solid child collider reaches
  grabRadius. grabRadius raised to 0.05 in the scene.
- Process decided: commit once per session, at wrap-up (root CLAUDE.md).
  This session's two interim commits were squashed into the wrap-up.
- Roadmap: ticked the in-headset gizmos item (reworded to the line-mesh
  approach), split step 6 into 6a test area (done) and 6b profiling
  (open), updated step 4 for the separate/eased returns, and added
  sub-items for front-only ladders and the solid rope + grab from inside.
- Still to do: step 6b profiling; the small pop when grabbing while a

2026-09-27 (second session)
---------------------------
- First periodic performance review (to be repeated now and then, so
  per-frame waste doesn't creep in). PlayerInputXR caches its resolved
  InputActions in OnEnable and guards Tick() with Time.frameCount - it was
  reading all nine actions twice a frame (its own Update() fallback plus
  PlayerController). HandRayReticle only toggles its renderer when
  visibility changes. PlayerHandInteraction pre-rotates the ray angle
  offsets once in Awake/OnValidate instead of a Quaternion.Euler per hand
  per frame. PlayerHandAnimation only calls SetFloat when a value changes.
  PlayerLocomotion: sqrMagnitude deadzone, isGrounded read once, jump
  launch speed cached, and the capsule re-centre skipped for head drift
  under 2mm (compared to the actual centre, so small moves still add up).
  Bug found doing this: XRI deactivating an untracked controller resets
  its Animator, so any "only set it when it changes" cache went stale
  after tracking loss (already true for the pose layer weight). Fixed with
  keepAnimatorStateOnDisable = true on both hand Animators.
  Learned: lookup tables don't pay for this kind of maths on Quest's ARM
  CPU (sqrt is one instruction) - hoisting work out of the frame does.
  Precomputing is worth planning into the AI/noise/visibility phases
  (cos of half the vision angle + a dot product for vision cones, squared
  distances, baked falloff curves). Rejected: caching tracked positions
  once per frame in PlayerTracking - they'd be stale after crouch and
  Move() mid-frame. Still to check in headset: finger curl after a
  controller loses tracking and comes back; the capsule following a slow
  lean smoothly.
- Physical hands step 3 - depenetration + rotation (Phase 1). Bug found
  first: a hand pushed into a wall with natural arm motion passed through,
  though walking into a wall with the arm held out stopped it. Cause: the
  wrist rotates as the arm moves, swinging the capsule into the wall at
  the START of the sweep - a CapsuleCast can't see anything it starts
  inside, so the "started inside, let it through" case fired. Confirmed by
  pushing in with the wrist locked (held fine).
  Fix: Depenetrate() runs before the sweep - OverlapCapsuleNonAlloc lists
  what the hand is inside (shared buffer, no allocation), then
  Physics.ComputePenetration gives the shortest way out of each, moved by
  that plus the skin width, up to 3 passes for corners. Before, not after:
  straight after a twist the overlap is shallow and the nearest way out is
  the side the hand came from; after a sweep the hand could be past the
  middle of a thin wall and get pushed out of the far side.
  ComputePenetration needs a real, ENABLED collider for the hand (Unity 6
  docs) but takes the pose as arguments, so each hand builds a trigger
  CapsuleCollider on PlayerHands, parked at y -1000 at the scene root and
  never moved.
  Then the hand drifted away from the wall the deeper it went - rotation
  again (wrist-locked: no drift). The arm pivots at the shoulder, so the
  wrist tilts as you push deeper, swinging the fingers into the wall, and
  the push-out backed the whole hand away. Fix: while in contact the hand
  keeps the rotation it touched with (replacing "always follow the
  controller"); contact only ends once the hand also fits at the
  controller's own rotation, otherwise it flickers on and off the wall.
  Rejected: freezing the hand with the snap system (no sliding, switches
  the finger pose, needs a snap pose on every surface) and pivoting about
  the contact point (complex, awkward with several contacts). The capsule
  maths now use the controller's rotation directly (GetCapsuleOffsets) -
  fine since everything from Player down to the controllers is scale 1.
- Physical hands step 4 - elastic band. When contact ends, the hand's
  offset from the controller - position and rotation, stored in the
  controller's own space - eases to zero over catchUpDuration (0.1s,
  SmoothStep), still swept every frame so it can land back in contact.
  Because the offset is relative to the controller, the hand keeps
  following the real hand while it eases back. Rejected: an exponential
  chase of the controller - it lags further the faster you move and might
  never settle. Snap-back: if a surface holds the hand more than
  maxSeparation (0.4m) away, it jumps straight to the controller and
  "passes through" (collision off) until the controller is clear.
  Without that the push-out moves it to the nearest face of whatever the
  controller is inside; if that's the near face it's too far away again
  and snaps back every frame.
- Physical hands step 5 - hand rays from the visual hand. Rays start from
  the controller pose shifted to where a surface holds the hand
  (HandPhysicalFollow.GetHandPose()), so a controller pushed through a
  wall can't target or grab what's behind it; the tuned ray angle offsets
  still apply. It's last frame's placement, since rays run before the
  visuals are ticked.
- UI draws after everything else (new project rule, in the root
  CLAUDE.md). The hand reticles and the mantle arrow were being hidden by
  walls and the hand models. CORRECTION to an earlier entry: the arrow
  never drew through walls. Its UI/Default material set unity_GUIZTestMode
  to Always, but that isn't one of the shader's material properties, so
  the override was silently ignored (the Inspector showed queue 4000, so
  the queue wasn't the problem). The reticle was depth-tested
  Sprites/Default. URP's Unlit has no depth-test setting either, so there's
  now a small shader of our own, TeaLeaf/Overlay
  (Art/Shaders/Resources): flat colour, ZTest Always, ZWrite Off, Cull
  Off, Overlay queue, with the single-pass instanced stereo macros so it
  draws in both eyes. It's in a Resources folder so Shader.Find() works in
  builds. Both markers build it through OverlayMaterial.Create().
- Scene setup bug: three test cubes had a ClimbableEdge on their own solid
  collider, on the Climbable layer - which collides with nothing, so hands
  and the player's body went straight through them. Split into solid
  cubes on Environment plus slightly larger trigger edge volumes (larger
  so the hand ray hits the edge first rather than tying with the solid
  face). ClimbableEdge.OnValidate() now warns about a non-trigger collider
  or the wrong layer.
- Learned: Game view gizmos don't work in VR - they're drawn for one flat
  camera, so they show in one eye only, offset. Use a Scene view on the
  monitor while playing, for now.
- Roadmap: physical hands steps 3-5 ticked, and the older duplicate items
  in that list resolved against what was built (rotation decision revised
  to "held while in contact"). Added an in-headset hand capsule debug
  visualiser (because of the gizmo problem). Step 6 (test area +
  profiling on Quest) is next session.

- Hand snap poses, step 2 of 3 (Phase 1). A general way for any grab
  target to say where a hand visual goes and how it's posed:
  HandPose (enum of finger poses), HandSnapPose (readonly struct: world
  position, rotation, pose) and IHandSnapTarget (GetSnapPose(isLeftHand,
  grabPoint)), all in Interaction. The target works out a model-agnostic
  "grip frame"; a shared HandSnapProfile ScriptableObject then applies
  per-hand position/rotation offsets (per hand because the right visual is
  mirrored). Chose a shared asset over per-edge fields so the offsets are
  tuned once for every ledge. ClimbableEdge implements it: the ray hit is
  moved to the box's top-front line in local space (clamped to the edge's
  length), facing into the wall. New convention: edge local X along the
  edge, +Y up, +Z out from the wall.
  HandVisualSnap (plain C# class, one per hand, owned by PlayerClimbing for
  now) blends the visual to the snap pose over 0.08s with SmoothStep and
  back on release, and skips touching the transform entirely at rest.
  Found while doing this: the old pinning ran inside PlayerClimbing.Tick(),
  before turning and Move() - since the visuals are children of the rig,
  every pinned hand was dragged off by that frame's movement until the next
  frame. Visuals are now placed in PlayerClimbing.TickHandVisuals(), a new
  last step (9) in PlayerController.Update(). Finger pose is carried in the
  snap pose but not played yet (step 3).
- Bug: snapping worked in headset, but a snapped hand still moved slightly
  with controller rotation/movement. Cause: the hands' Tracked Pose Drivers
  use "Update And Before Render" (m_UpdateType 0), so just before rendering
  - after all our Update() code - they move the controller again with
  fresher tracking data, dragging any child visual with it. Setting the
  pose later can't beat that reliably (before-render callback order isn't
  guaranteed). Fix: HandVisualSnap detaches the visual (SetParent(null,
  true)) on snap and re-attaches it to the controller when the release
  blend ends. Parented to the scene root rather than the ledge, because the
  ledges are non-uniformly scaled cubes and a rotated child under one would
  shear. Lesson: anything that must stay world-fixed can't be a child of a
  tracked transform. Verified in headset - snapped hands now stay dead
  still on the ledge. Step 2 done.
- Committed as two commits: MovementState (code only), then the climb
  grab + snap poses together with the scene and all doc updates, since
  those files mixed changes from both.
- Hand snap finger pose, step 3 of 3 - code side (Phase 1). Chose a new
  "Snap Pose" override layer on top of the hand controller over forcing
  TriggerCurl/GripCurl to 1 (that only gives a closed fist, not fingers
  hooked over a lip, and every future pose would need more parameters).
  The layer's states are named after HandPose values, hashed once from the
  enum names, so a new pose is an enum value + state + clip with no new
  code. Its weight is HandVisualSnap's new Weight (the eased snap blend),
  so the fingers close exactly as the hand lands and open as it leaves -
  one source of timing. Removed PlayerHandAnimation's HandState enum:
  every non-input pose is now a snap pose, so the snap weight already says
  who owns the fingers; the input layers always run underneath.
  PlayerHandAnimation.Tick() moved to the end of the frame (after
  TickHandVisuals) so it reads this frame's weight - free, since Animators
  evaluate after all Update() calls anyway. Updated roadmap items that
  mentioned HandState.
- Bug: with the Snap Pose layer + LedgeGrip clip in place, the index
  finger hooked correctly but middle/ring/pinky looked like the grip
  animation. The clip only keyed joint 2 of each finger, and a layer only
  overrides the bones its clip keys - joints 1 and 3 kept the Grip layer's
  curl, which is fully closed because grip is held to climb (the index

  not-yet-animated bone, and pose clips used in blend trees need exactly ONE

  within a single clip - otherwise the Animator plays that clip's own
